# ex-15 branch

**Covers:** the ex-15 branch, its feature programme, and its topology relative to master.

## Overview & topology

- Purpose: next major version (15.x), planned since 2018; user's last major manual work was 2022;
  contributor work has continued since [RECOLLECTION:2026-09-05].
- Version: the 15.x line, with a new Extended savegame series → [savegame-versioning](savegame-versioning.md).
- Topology: master→ex-15 merges happen periodically; ex-15 contains a large unique commit history;
  derive current state with git at task time; do not cache.
- New code vs. master: `dataobj/consist_order_t.{cc,h}`, `dataobj/schedule_entry.h` (split out of
  schedule.h), `gui/consist_order_gui.{cc,h}`, plus extensive schedule/economy/vehicle rework.
  The inflation API (`karte_t::get_inflation_adjusted_price`) exists only on ex-15, not master.
  The SDL3 backend exists on both branches.
- Touch hotspots: the convoy system, the schedule system and its GUI, the consist-order GUI,
  vehicle-list/detail GUI, vehicle descriptors, convoy assembler, settings.

## Feature programme status

The programme is the set of balance-critical features for 15.x defined in the forum threads listed
below. Most features were implemented circa 2022 (forum implementation reports Jun 2022–Jan 2023:
[FORUM:https://forum.simutrans.com/index.php/topic,17852.msg200693.html],
[FORUM:https://forum.simutrans.com/index.php/topic,17852.msg202994.html])
[RECOLLECTION:2026-09-07].

Consist re-combination is NOT complete. Both runtime recombination paths exist on ex-15. The Y
division (one convoy splitting into two portions at a stop, each continuing on its own schedule): an
entry flagged `uncouple` without `couple` divides in `convoi_t::hat_gehalten`, the retained portion
keeps the source entry's consist order, and the split-off portion receives the target line's
schedule, or a copy of a lineless target convoy's schedule, starting at the target entry. The paired
H exchange (two convoys exchanging vehicles at one stop as one operation): the receiver's entry
carries `couple` and the target's entry carries `uncouple`, `convoi_t::resolve_paired_exchange`
validates that the two entries name each other at the same stop, the file-local
`paired_exchange_solver_t` in `simconvoi.cc` finds a disjoint pair of powered final consists that
satisfy both consist orders, and `convoi_t::commit_paired_exchange` replaces both consists as one
operation. The scripted Y baseline, the scripted paired-exchange cases, the Y division's loopback
network join with the existing save/transfer/reload, and a fresh offline load of that join save all
pass [EXECUTION-VERIFIED:2026-11-13]. Still outstanding: freight and passenger continuity across a
split or join (including the intended loose-stock treatment, which keeps the load associated with a
discharged vehicle and credits its loading time retrospectively when it is collected), platform and
call-on handling for coupling movements, reversal-aware vehicle picking, the per-portion validity
gate, the GUI authoring-time pre-check in the schedule windows, and save/network reload coverage of
a paired exchange. The through-journey path-explorer traversal (the
connexion rebuild through connexions across couplings where portions join or split) is implemented
[RECOLLECTION:2026-09-07; CODE ex-15 @ 684d570f9 plus working-tree recombination runtime]. The
consist-order GUI was declared the programme blocker in Feb 2023
[FORUM:https://forum.simutrans.com/index.php/topic,17852.msg203144.html]; Ranran's UI work
(branches through ex15-2401/ex15-2402) is merged into ex-15. Operational requirements, design
decisions and implementation ordering: [recombination-design](ex-15/recombination-design.md).

Per-feature status registry (code-first; intent vs implemented state vs gaps):

- [schedule-and-consists](ex-15/schedule-and-consists.md) — read when touching schedule entries,
  consist orders, re-combination (couple/uncouple/layover/triggers/range stops), or the schedule
  GUI on ex-15.
- [economy-and-vehicles](ex-15/economy-and-vehicles.md) — read when touching vehicle wear/overhauls/
  availability, depot maintenance, fuel/staff/prices.tab inflation, or the replacer on ex-15.
- [path-explorer-optimisation](path-explorer-optimisation.md) — read when touching the route-search
  tables or their performance/threading. The search runs one shortest-path search per origin over
  a graph whose states are (stop, transport used to arrive), built from every walking, ride and
  through-journey candidate between stops. A pool of worker threads processes the origins; each
  stored route entry costs 6 bytes per stop pair, and the savegame format is
  versioned by `EX_SAVE_MINOR` (see [savegame-versioning](savegame-versioning.md)). A separate,
  standalone implementation of the same search reproduces its route times exactly; next
  transfers differ only where two routes tie on time. On the gargantuan Bridgewater-Brunel save
  a complete rebuild takes about a minute and peaks at 3,880 MB of working-set memory. Through
  journeys (staying aboard across a coupling where portions join or split) and comfort-based
  route choice are implemented. Comfort-based route choice adds about 20% to a complete rebuild
  with no per-step time limit: 57.1 s without it and 68.6 s with it, four threads. The remaining
  comfort-routing tasks are in
  [comfort-routing](path-explorer-optimisation/comfort-routing.md). Hub labels, a compact
  alternative representation of the route tables, were assessed and rejected: the labels exceed
  the size of the full table before they cover all stop pairs, and building them is much slower
  than the current search (see [hub-labels](path-explorer-optimisation/hub-labels.md)). A GPU
  implementation of the graph search has not been assessed. The work stays on ex-15 until 15.x
  merges into master [CODE ex-15 @ 5eda2829e; comfort performance
  EXECUTION-VERIFIED:2026-11-09].

## Merge strategy & change placement

- Major new features go on ex-15. Bugfixes and minor enhancements go into master and are then
  merged from master into ex-15 immediately unless there should be a very good reason to do
  otherwise. This applies to ALL master changes (code, build/CI and docs alike): while ex-15
  development remains ongoing, master merges into ex-15 immediately
  [RECOLLECTION:2026-09-07]. ex-15 will eventually be merged into master when it is ready for
  release [RECOLLECTION:2026-09-07].
